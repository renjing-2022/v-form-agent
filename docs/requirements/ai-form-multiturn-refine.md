## 1. 背景与问题

`v0.1.0` 已交付「自然语言 / Excel → 整表生成 → 确认写画布」闭环，但明确不做对话式增量修改。业务侧在已有表单（导入、手拖、手改后）上，仍需通过自然语言继续调整结构、字段选项与计算关系，而不是每次另起一张表。

## 2. 终局目标（分阶段达成）

用自然语言多轮会话，对**当前画布最新** `formJson` 进行配置优化，最终覆盖：

- 全量 v-form 组件与合理嵌套（含 tab / grid 等容器）；
- 字段 `options` 与布局结构调整；
- 自定义 CSS、事件脚本与业务交互（含计算类逻辑）。

终局能力分多版本交付；**本版本只验收 P0**。

## 3. 本版本目标（P0）

1. 在保留「无表 / 空画布时整表生成」入口的同时，支持基于**当前表单**的多轮优化对话。
2. 每轮请求使用设计器 `getFormJson()` 得到的最新配置（含导入、手拖与手动微调）。
3. 会话历史存放在**前端内存**（后续版本可再评估服务端会话）。
4. 优化范围限定为：**结构变更、字段 options、公式（formula）**；确认后整表覆盖写回画布。
5. Agent 侧扩展组件知识/白名单，使常见容器与字段（含 tab 等）可按 `widgetsConfig.js` 规则组装，并由代码校验后返回。

## 4. 非目标（本版本不做）

- 自由编写 / 自动生成自定义 CSS（`cssCode` 大段样式）；
- 自由编写任意事件 JS（`onChange` 等通用脚本）作为主路径；
- 服务端持久化会话、多租户会话存储；
- PDF / Word / 图片 OCR；
- 生产级独立部署变更。

以上能力写入终局路线，留给后续版本（如 P1：受控 CSS/事件）。

## 5. 用户与场景

| 编号 | 场景 | 成功标准 |
|---|---|---|
| S1 | 空画布整表生成 | 沿用 v0.1.0 生成入口，仍可生成并确认应用 |
| S2 | 已有表多轮优化 | 对当前 JSON 连续两轮以上指令后，预览结果反映累计意图，确认后画布更新 |
| S3 | 结构优化 | 可用自然语言增加容器/字段（如 tab 分区）或调整字段归属 |
| S4 | 选项与公式 | 可改 select/radio 选项；可用公式表达简单计算字段 |
| S5 | 确认覆盖 | 未确认不写画布；确认后 `loadFormJson` 整表覆盖；校验失败保留原画布 |

## 6. 功能需求

### FR-1 双模式入口

- **生成模式**：无表或用户明确要求整表生成时，沿用现有 generate 能力。
- **优化模式**：画布已有控件时，默认进入基于当前 `formJson` 的多轮优化。

### FR-2 多轮会话（前端内存）

- 前端保存本会话消息与最近一次可应用结果；
- 刷新页面可清空会话（P0 可接受）；
- 每轮提交携带：用户话术、会话摘要/历史、**当前** `formJson`。

### FR-3 结构与 options 优化

- 支持增删改字段、调整类型与 options（如选项文案/分值）、常见容器嵌套（至少含 tab）；
- 尽量保留未改动控件的 `id` / `name`，降低手改丢失。

### FR-4 公式优化

- 支持对适用字段启用/调整 `formula`（优先于手写 JS）；
- 无法可靠落地的计算进入 `warnings`，不得写非法配置。

### FR-5 确认写回

- 返回 `{ summary, warnings[], formJson }`；
- 用户确认后整表 `loadFormJson`；校验失败不写画布。

### FR-6 文案修改边界（禁止「改字冒充样式修复」）

- 表单字段的 **label、textContent、选项 label** 等展示文字，**仅当**用户话术**明确**要求改文案/改标题/改选项文字时，才允许通过 refine 修改。
- 用户描述 **样式、布局、对齐、间距、重叠、颜色、字体** 等视觉问题时：
  - **禁止**通过缩短/改写 label 或 optionItems 文案来使问题「看起来消失」；
  - 应通过 `warnings` 说明 P0 不支持自由 CSS，引导用户手动样式或改用允许的结构/options/公式指令。
- 未明确要求改文案时，refine 对未提及字段的文案必须保持不变（与 FR-3 的 id/name 保留策略一致）。

## 7. 验收标准（产品层）

1. 空画布仍可完成至少一次整表生成并应用。
2. 在已有表（含手改细节后的最新 JSON）上，连续多轮优化指令可得到可预览的合规 formJson，确认后画布反映优化结果。
3. 至少覆盖：一类结构变更（如增加 tab 或调整分区）、一类 options 变更、一类公式字段变更（或明确 warnings 降级且不破坏画布）。
4. 未确认前画布不被静默覆盖；非法结果有可读错误。
5. DeepSeek Key 仍仅存在于 Agent 服务端。
6. 样式/布局类指令在未明确要求改文案时，不得静默修改字段或选项文字；若无法通过允许能力解决，应给出可读 warning 或拒绝（422），而不是改字规避。

## 8. 约束与假设

- 模型：DeepSeek 云 API；
- 规范真源：`widgetsConfig.js` + `getDefaultFormConfig()`；
- 合入策略：模型规划意图，代码组装/合入与校验（禁止把未校验的模型自由 JSON 直接当画布数据）；
- 应用策略：整表确认覆盖。

## 9. 风险

- 深嵌套与全组件知识不全导致组装失败率高 → P0 以可校验白名单+模板扩展为主，失败进 warnings/错误；
- 整表覆盖误伤未表达的手改 → 尽量按 id/name 保留未改节点，并在 UI 提示「确认将覆盖当前表」；
- 大 JSON 多轮超上下文 → 可做摘要/裁剪，但必须以每轮最新 formJson 为真相源。
- LLM 为规避 P0 无 CSS，可能改文案冒充样式修复 → 产品/Planner/代码三层约束（见 FR-6 与 issue `docs/issues/refine-no-text-for-style.md`）。

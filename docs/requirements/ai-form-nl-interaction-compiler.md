## 1. 背景与问题

用户目标：**基于现有表单，用自然语言描述页面交互，模型直接写出 JS，并保证在真实表单里跑对。** 典型需求：

> 在每个 tab 下新增一个「下一页」按钮，点击时校验当前 tab 的字段，校验通过跳到下一个 tab，失败则定位到第一个出错的字段。

v0.8 无法完成这类需求，根因：

1. **没有理解能力。** `/event` 生成器是正则 + 固定模板，模型不参与。
2. **结构与行为分裂。** 结构只能走 `/refine`、事件只能走 `/event`；`button` 不在新建白名单。
3. **要求用户写测试用例。** 必须手写「期望：{...}」。
4. **关键词路由。** 复杂描述被误送到 `/refine`。

修订 1 曾设计「模型只出计划、编译器生成 JS」，其表达能力受限于预定义步骤集合，与用户目标不符，修订 2 废弃该方案。

v0.8 保留的资产：状态机思路、真实预览执行闸、服务端重判、覆盖保护。

## 2. 已锁定决策（2026-09-23）

| 决策项 | 选择 |
|---|---|
| 代码生成 | **DeepSeek 直接写事件 JS**，不经过中间 DSL；可使用任意纯前端 JS 能力 |
| 代码禁区 | **只禁网络请求**（接口、数据源、上传）；DOM、定时器、`eval`、跳转、本地存储等不禁止 |
| 正确性保证 | 模型同时写出**验证场景**；系统在真实预览中执行；失败原因回传模型自动修正 |
| 确认环节 | 写入前向用户展示：结构变更、事件代码、验证场景及其真实执行结果；用户确认后写入 |
| 范围 | 纯前端交互 |
| 能力面 | 字段联动、Tab / 分步向导、按钮动作、子表计算、提交前校验、打开时初始化（**v0.9 一次做完**），且不限于此 |
| 验收题库 | Agent 起草、**用户已审阅**（下限用例；复杂场景靠多轮澄清） |
| 模型验证 | 验收用录制回放保证可重复；另含真实 DeepSeek 冒烟（用户提供 Key） |

## 3. 版本定位

> 一句话进来 → 模型产出「结构变更 + 事件 JS + 验证场景 + 说明」→ 在真实预览中执行全部场景 → 失败自动回传修正（有上限）→ 把代码、场景与真实结果展示给用户 → 用户确认后，结构与事件作为一个整体写入画布。

「一步到位」的定义：**纯前端范围内，模型能写出来、且其验证场景在真实表单中全部通过的交互，都能写入**；涉及网络请求或验证不通过的，诚实说明、不写入。题库是验收下限；更复杂的真实需求通过多轮对话（`need_clarification` / 用户补充）澄清后，仍由模型像前端程序员一样直接写 JS。

## 4. 端到端流程

```text
用户描述
  ↓ action=generate
DeepSeek → { structure, handlers(JS), scenarios, summary }
  ↓ 格式校验 + 引用校验 + 网络请求检查（失败回传模型重写）
status=generated
  ↓ 前端在真实预览中执行全部场景 → verificationReport
  ↓ 有失败 → action=repair（附失败场景与报错）→ 重新执行；最多 2 轮
status=verified / failed：展示代码、场景、真实结果
  ↓ 用户确认（仅 verified 可确认）
action=apply（服务端按场景断言重判）→ applied；否则 draft，画布不变
```

## 5. 功能需求

### FR-1 统一交互入口

- AiChat 不再用关键词分流；统一入口由模型判定意图：交互 / 结构+交互 / 纯结构 / 需澄清 / 超出范围。
- 纯结构需求交给现有 `/refine`，行为不变。
- `/event`（v0.7/v0.8）保留为兼容端点，回归通过即可。

### FR-2 模型直接生成交互 JS

- 模型输入：formSummary（字段、容器、tab 页及其字段归属、按钮、子表列、已有事件代码）、VForm 渲染态 API 参考手册、事件键与执行上下文说明、用户描述与多轮上下文。
- 模型输出 `handlers[]`：每项为 `{ target(控件名或 form), eventKey, code, explain }`，`code` 是事件函数体。
- JS 写法不限：条件、循环、Promise、正则、日期、定时器、DOM、`eval` 等均可。
- 引用的控件必须在表单中存在或在本次结构变更中新建；不满足则回传模型重写。
- API 参考手册只是提示，不是白名单；调用不存在的方法会在真实执行时报错并触发修正。

### FR-3 结构 + 行为同一事务

- 输出可包含结构变更：复用 refine 操作集，新增 `addButton`（可「在每个 tab 页末尾各加一个」）。
- `button` 仅在本管线允许新建；`/refine` 新建白名单不变。
- 结构与事件一起验证、一起写入；任一失败则都不写。

### FR-4 验证场景由模型给出

- 模型为每个 handler 至少写 1 个场景；有条件分支的交互需覆盖成立与不成立两侧（例如「下一页」：当前页有必填为空 / 已填齐 / 末页）。
- 场景结构：`arrange`（预置字段值、当前 tab）→ `act`（输入、点击、切 tab、装载、增行、提交校验、等待）→ `assert`（可观察状态）。
- 可断言状态：字段值、hidden、disabled、required、label、当前 tab、焦点字段、校验结果、弹窗可见性、子表行数、是否发生网络请求、运行时报错。
- 用户不需要写任何示例。

### FR-5 网络请求禁止

- 静态检查：直接出现的 `fetch`、`XMLHttpRequest`、`WebSocket`、`EventSource`、`navigator.sendBeacon`、动态 `import()`、axios 等，以及 VForm 数据源请求方法，判为违规并回传模型重写。
- 运行时检查：验证期间拦截网络 API，任何请求都使该场景失败（用于兜住 `eval` 等动态写法）。
- 其他 JS 能力不设禁区。

### FR-6 真实预览验证、自动修正与写入闸

- 在真实 VFormRender 预览中执行场景（沿用 v0.8：真实触发、只报读到的状态、读不到判失败）。
- 失败时把失败场景、期望与实际、运行时报错回传模型修正代码，最多 2 轮；模型不得通过修改场景断言来「修正」（服务端比对场景是否被改动）。
- 服务端按场景断言重判 `verificationReport`；客户端的 `ok/pass` 不可信。
- 仅全部场景通过才可确认写入；否则 `draft`，画布不变。
- 目标事件已有手写代码：沿用 v0.8 覆盖确认策略。

### FR-7 写入前确认

- 展示：模型说明、结构变更清单、每个事件的代码、每个场景的中文描述与真实执行结果。
- 场景描述由场景数据确定性渲染，用户确认的就是被验证过的内容。
- 用户可修改描述重新生成；未确认不写入。

### FR-8 诚实失败

- 需要网络请求（接口、数据源、上传）：说明不支持，不写入，不用占位控件凑数。
- 修正轮次用尽仍失败：展示失败场景与报错，`draft`。
- 模型不可用（无 Key、超时、配额）：返回明确错误，不降级成正则模板。

## 6. 能力面（v0.9 全部交付，题库覆盖）

| 编号 | 能力 | 典型描述 |
|---|---|---|
| C1 | 字段联动 | 数量或单价变化时自动算金额；选「其他」时显示说明框并设为必填；A 为空时禁用 B；按条件改标签 |
| C2 | Tab / 分步向导 | 每页加上一页/下一页；按页校验；失败切到出错字段所在页并聚焦；末页提交按钮 |
| C3 | 按钮动作 | 重置表单、清空指定字段、填充默认值、打开已有弹窗 |
| C4 | 子表 | 行内计算（单价×数量）；合计汇总到主表字段；增行时带默认值 |
| C5 | 提交前校验 | 跨字段规则（结束日期不早于开始日期、合计不超过预算）；不通过时阻止提交并定位 |
| C6 | 打开时初始化 | 设置默认值、初始显隐/禁用、默认激活某个 tab |

能力面不是上限：模型写出且验证通过的其他纯前端交互同样可写入。

非目标：网络请求（接口、`dataSources`、上传）；列 `render`；智能合并手写事件；跨表单通信。

## 7. 验收

- 题库（`scenarios.md`）每条正例：generated → 真实预览全部场景通过（可含自动修正）→ 用户确认 → applied 后设计器 JSON 中结构与事件均存在 → **再用题库的独立断言在 Playwright 中复验**（不只信模型自己写的场景）。
- 题库负例：不可 apply、画布不变、给出原因或澄清问题。
- **确定性回放：** 题库的模型输出（含修正轮）录制为 fixture，验收在 mock 模式下回放。
- **真实冒烟：** 用真实 DeepSeek 跑题库子集（≥5 条，含「下一页」），记录通过率；证据中不含 Key 与完整请求头。
- 回归：v0.8 全部 26 个用例；v0.7 澄清；v0.6 重型容器；formula；strict sweep；frontend-no-secret。

## 8. 能力天花板

- **能保证：** 写入的代码在其验证场景下于真实表单中通过；验证期间无网络请求；写入要么全部成功要么不写。
- **不能保证：** 场景之外的输入组合；模型对含糊描述的理解一定符合本意（由用户确认场景兜底）；生成代码的风格与可读性一致。
- **已知取舍：** 放开 `eval`、DOM、跳转、本地存储后，静态检查只能发现直接写出的网络调用；动态写法依赖验证期运行时拦截，场景未覆盖的分支中的动态网络调用无法保证被发现。

## 9. Breaking（相对 v0.8）

| 位置 | v0.8 | v0.9 |
|---|---|---|
| AiChat 路由 | 关键词分流 `/refine` / `/event` | 统一入口，模型判定 |
| 交互生成 | 正则模板 | 模型直接写 JS |
| 代码限制 | AST 白名单（禁 DOM、定时器、eval 等） | 本管线仅禁网络请求；`/event` 保持 v0.8 规则 |
| 用户示例 | 必须写「期望：{...}」 | 不需要，模型写场景 |
| 新建 button | 不允许 | 交互管线内允许 |
| 写入单位 | 单个事件键 | 结构 + 事件整体事务 |

## 10. 风险

见设计文档 §9。核心：模型代码与场景同源（可能一起错）、模型改场景迁就代码、动态网络调用漏检、验证期副作用（跳转、存储、定时器）、异步时序、状态可观察性。
